# Dialogue-State Follow-up Case Design

## Background

The current `bridgebench_cp_heldout_v2_50_draft.jsonl` mainly covers real-problem-grounded initial help-seeking turns: the student opens AIChat and asks questions such as “How should I think about this problem?”, “What should `check` mean?”, or “How do I define the state?” This is useful for testing initial missing-bridge diagnosis, but it does not fully evaluate the core tutoring behavior: adjusting scaffold granularity after the student responds to a prior scaffold.

We therefore need a dialogue-state case layer for follow-up tutoring turns:

```text
student initial question
-> fixed context AI gives a light scaffold question
-> student gives a short, partial, wrong, or confused answer
-> evaluated system generates the current tutor response
```

This design does not replace held-out v2. It creates a v3 draft on top of the v2 real problem-source foundation.

## Goals

1. Measure whether the tutor can respond to the student’s previous answer instead of restarting the explanation.
2. Measure whether the tutor adapts scaffold granularity to the student’s followability.
3. Keep all baselines under the same fixed context, avoiding contamination from a prior response generated by one evaluated condition.
4. Support paper analysis of contingent scaffolding / adaptive scaffolding.

## Non-Goals

- Do not generate a complete real multi-turn teaching experiment.
- Do not claim the synthetic dialogues are verbatim real student utterances.
- Do not use historical online AI replies as generation inputs for evaluated systems.
- Do not let one baseline generate prior context and another baseline continue from it.

## Core Fields

Add or strengthen these fields:

```json
{
  "turn_position": "initial|followup",
  "context_type": "initial_question|followup_after_correct_short_answer|followup_after_partial_answer|followup_after_wrong_answer|followup_after_code_attempt|followup_after_prerequisite_gap",
  "student_scaffold_followability": "F1|F2|F3|F4",
  "followability_label_confidence": "high|medium|low",
  "followability_evidence_quote": "...",
  "followability_uncertainty_reason": "...",
  "prior_ai_scaffold": "...",
  "student_reply_to_prior_scaffold": "...",
  "expected_tutor_move": "advance|clarify|micro_step|prerequisite_repair|safe_redirect",
  "fixed_recent_dialogue_source": "synthetic_dialogue_state_v3"
}
```

`recent_dialogue` remains the final runner-facing context field, but the v3 generator should build it from `prior_ai_scaffold` and `student_reply_to_prior_scaffold`.

## Student Scaffold Followability

`student_scaffold_followability` should not be a loose expert impression. It must be determined from the prior `prior_ai_scaffold` and the student’s `student_reply_to_prior_scaffold`, so that it can be annotated, reviewed, and reported as a learner-state field.

Annotators judge only how the student responded to the previous scaffold question. They should not change the label based on a broad guess about whether the student is generally strong or weak.

| Level | Name | Observable evidence | Current tutor response should |
| --- | --- | --- | --- |
| F1 | Can follow | Student answers the prior question; direction is correct; no clear conceptual confusion; ready to proceed | Briefly confirm and advance to the next small bridge |
| F2 | Partially follows | Student is directionally right but vague, incomplete, still uncertain, or answers only part of the prior question | Confirm the correct part, then ask one finer question |
| F3 | Struggles to follow | Student answers the wrong question, confuses the key concept, gives an incorrect judgment, or only says they do not know | Lower granularity with a tiny example, local observation, or binary check |
| F4 | Prerequisite gap | Student cannot understand a prerequisite concept, notation, data-structure object, or basic code meaning used in the prior scaffold | Pause problem-specific progress and repair the smallest prerequisite |

### Decision Rules

1. First inspect the prior AI scaffold question; then inspect whether the student answered that question.
2. If the student’s answer is correct and ready to advance, label F1.
3. If the answer is directionally correct but incomplete, label F2.
4. If the answer is wrong, off-target, or unable to handle the current small question, label F3.
5. If the student lacks a prerequisite needed to understand the prior scaffold itself, label F4.
6. If the label cannot be determined, set `followability_label_confidence=low` and fill `followability_uncertainty_reason`; do not force every case into a confident F1-F4 label.

### Evidence And Confidence

Every follow-up case must include:

```json
{
  "followability_label_confidence": "high|medium|low",
  "followability_evidence_quote": "...",
  "followability_uncertainty_reason": "..."
}
```

Requirements:

- `followability_evidence_quote` must quote the student’s reply to the prior scaffold.
- Low-confidence cases must not enter headline metrics; they can be used for error analysis or adjudication.
- If the evidence is insufficient, revise the case instead of forcing a label.

### Disagreement Adjudication

F1-F4 is a new educational judgment field. Before the formal experiment, use partial double annotation:

```text
Coach A labels all v3 follow-up cases.
Coach B independently labels at least 20 follow-up cases.
Report F1-F4 agreement, adjacent-level weighted agreement, and low-confidence rate.
Adjudicate disagreement cases.
```

Adjacent disagreements such as F1/F2 or F2/F3 are acceptable and should be reported. Non-adjacent disagreements such as F1/F3 or F2/F4 should trigger a review of whether the case itself is underspecified.

## Recommended Distribution

For a 50-case dialogue-state v3 draft:

| Type | Count | Notes |
| --- | ---: | --- |
| initial_question | 10 | Keep initial help-seeking turns for comparability with v2 |
| followup_after_correct_short_answer | 7 | F1, student can follow |
| followup_after_partial_answer | 8 | F2, student is partly right |
| followup_after_wrong_answer | 7 | F3, student understanding is off |
| followup_after_code_attempt | 10 | Student posts code or a faulty implementation |
| followup_after_prerequisite_gap | 5 | F4, student needs prerequisite repair |
| policy/direct-answer special | 3 | Direct answer/code safety cases |

This distribution is not final; it can be adjusted after coach review, but follow-up turns should be the majority.

## Examples

### F1: Can Follow

```text
学生：这题为什么要二分？
AI：先看候选值 x 变大时，条件是更容易满足还是更难满足？
学生：x 越大越难满足。
```

The current tutor should confirm this observation and ask the student which side remains after true/false. It should not restart a full binary-search explanation.

### F2: Partially Follows

```text
学生：check 里面 true 到底是什么意思？
AI：你先拿一个很小的候选值试一下，看看它表示“能做到”还是“做不到”。
学生：应该是能做到吧，但我不知道后面往哪边。
```

The current tutor should confirm whether “can do” matches the problem, then ask the student to compare feasibility when the candidate increases or decreases.

### F3: Struggles To Follow

```text
学生：dp 这一格是啥意思？
AI：先说这一格对应“处理到哪一步”。
学生：是不是记录答案？我不确定。
```

The current tutor should lower granularity, asking the student to separate “index means range/position” from “value means objective quantity.” It may use a tiny observation but must not give the full state definition.

### F4: Prerequisite Gap

```text
学生：lazy 到底表示啥？
AI：先看一个节点 [1,2]，如果整段加了 5，但还没往两个叶子递归，你觉得叶子现在真的改了吗？
学生：我不太懂节点和叶子是什么意思。
```

The current tutor should pause lazy details, explain the smallest prerequisite about segment-tree nodes/leaves/interval coverage, then return to the problem.

## Generation Principles

1. `prior_ai_scaffold` must be fixed and must not belong to any evaluated condition.
2. `prior_ai_scaffold` should be a light scaffold and must not reveal the full critical bridge.
3. `student_reply_to_prior_scaffold` should be short and natural, not an ideal answer.
4. F1/F2/F3/F4 should reflect different followability states, not merely different text lengths.
5. Code cases should allow students to paste code and ask a short question.
6. The generator should preserve real problem-source fields and v2-compatible fields to avoid major runner changes.

## Evaluation Impact

Response blind-review workbooks should show:

- original / necessary problem statement;
- fixed recent dialogue;
- student response to the prior AI scaffold;
- current target AI response for review.

Additional review focus:

- whether the tutor responds to the student’s previous answer;
- whether the tutor correctly infers followability;
- whether it chooses the right tutor move;
- whether it lowers granularity in F3/F4 cases instead of pushing a full solution.

## Paper Wording

> We evaluate both initial help-seeking turns and follow-up tutoring turns. In follow-up turns, the tutor observes a fixed prior scaffold and a short student response, then must decide whether to advance, clarify, micro-scaffold, or repair prerequisite understanding.

## Acceptance Criteria

- The v3 generator does not overwrite v2 files.
- v3 cases pass held-out dataset validation, or a v3-specific validator is added.
- Every follow-up case includes `student_scaffold_followability` and `expected_tutor_move`.
- Every follow-up case includes `followability_evidence_quote` and `followability_label_confidence`.
- Low-confidence followability cases are marked and excluded from headline metrics.
- Prior AI context in `recent_dialogue` is not generated by any evaluated baseline.
- Review workbooks display fixed context and current target AI response.
- Documentation and data clearly state synthetic-but-grounded status and do not claim verbatim real student utterances.
