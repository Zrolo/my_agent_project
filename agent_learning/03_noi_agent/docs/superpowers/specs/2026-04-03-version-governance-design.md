# NOI Coach Version Governance Design

## 1. 目标

给当前项目建立一套统一的版本治理规则，让后续版本号不再依赖零散命名，而是稳定表达：

- 当前产品处于哪个阶段
- 每个阶段的核心目标是什么
- 每次大更新和小更新分别意味着什么
- 已发生的更新应记录到哪里

本设计只解决版本治理与记录方式，不改业务代码，不替代 task plan，不替代 harness。

---

## 2. 设计结论

项目从现在开始采用以下版本体系：

- 大版本：`V1`、`V2`、`V3`
- 小版本：`V1.01`、`V1.02`、`V1.03`

版本号以产品里程碑为主，不以代码改动量为主。

只有当学生使用体验或教学闭环进入新阶段时，才升大版本。

同一阶段内的成体系增强、质量收紧、体验改良、工程维护，升小版本。

---

## 3. 文档结构

版本治理采用三份项目级文档，统一放在 `docs/common/`：

### 3.1 `version_policy.md`

职责：

- 定义版本号规则
- 定义大版本与小版本的升级条件
- 定义版本状态与记录规范

只写规则，不写某一轮具体更新内容。

### 3.2 `version_plan.md`

职责：

- 记录当前项目所处版本
- 记录 `V1` 的阶段目标
- 记录 `V1.xx` 的路线图
- 粗略记录 `V2`、`V3` 的后续方向

只写未来规划，不写已发生更新明细。

### 3.3 `changelog.md`

职责：

- 记录已经发生的版本更新
- 每条更新同时包含“产品变化”和“工程摘要”

只写已发生变化，不写未来打算。

不单独建立 `update.md`。原因是这个命名过于泛，后续容易变成无边界流水账；`changelog.md` 更稳定，也更容易长期维护。

---

## 4. 版本规则

### 4.1 大版本规则

从 `V1.x` 升到 `V2`，必须满足以下原则：

- 学生体验发生阶段变化
- 或教学闭环进入新阶段

这里的“新阶段”指的不是单个模块增强，而是系统能力边界改变，例如：

- 从“能提供 AI 复盘”进入“能稳定完成复盘 + quiz + remedy 闭环”
- 从“规则型推荐”进入“稳定个性化训练路径”
- 从“以人工调参为主”进入“以稳定评测与版本治理为主”

### 4.2 小版本规则

`V1.01`、`V1.02` 这类小版本用于记录同一阶段内的成体系更新，例如：

- AI 复盘质量收紧
- quiz / fallback / confirm 规则收紧
- 学生端工作台体验增强
- 教师端运营能力增强
- 题库与 problem analysis 质量增强
- 一轮明确边界的工程整理

不要求每个 commit 都对应一个小版本。

只有当一轮更新在产品或系统层面形成稳定主题时，才升一个新的 `V1.xx`。

### 4.3 版本状态

每个版本可使用以下状态：

- `planned`
- `in_progress`
- `released`
- `archived`

含义：

- `planned`：已进入版本路线图，但尚未开始
- `in_progress`：已经围绕该版本主题推进
- `released`：该版本目标已达到当前定义的完成线
- `archived`：保留历史记录，不再继续扩写

---

## 5. 当前项目的起始版本

从本次版本治理建立开始，统一采用以下基线：

- 当前主版本：`V1`
- 当前正式小版本起点：`V1.01`

原因：

- 项目仍处于前期
- 学生端工作台、复盘、quiz、harness 已经建立基础框架
- 但整体仍处于“第一阶段闭环搭建与质量收紧”阶段

因此，`V1.01` 代表：

- 项目正式进入统一版本治理
- 第一阶段产品骨架已经成立
- 后续在 `V1` 阶段内继续通过 `V1.02`、`V1.03` 推进质量和体验

旧文档中的 `v1.2`、`2.1` 等命名保留原样，视为历史阶段材料或实验命名，不作为新的统一版本治理基线。

---

## 6. 版本路线建议

当前建议把 `V1` 理解为“第一阶段 NOI 教练闭环跑通”。

建议路线如下：

### `V1.01`

建议定义为：

- 版本治理建立
- harness 体系已落地
- 学生端工作台主结构成立
- review / quiz 质量门已建立

### `V1.02`

建议定义为：

- AI 复盘质量收紧
- `key_bridge / next_step` 更稳定
- 高风险 focus 的 review 漂移显著减少

### `V1.03`

建议定义为：

- quiz / fallback / confirm 进一步收紧
- 坏题率下降
- 结构事实题与 fallback 边界更稳定

### `V1.04`

建议定义为：

- 题库推荐、problem analysis、教师端运营能力增强

### `V2`

建议在以下条件接近成立时再考虑：

- 学生端形成稳定的个性化训练闭环
- 版本治理、评测、迭代方式进入更成熟阶段

---

## 7. 三份文档的建议结构

### 7.1 `version_policy.md`

建议包含：

- 版本治理目的
- 编号规则
- 大版本升级条件
- 小版本升级条件
- 版本状态定义
- 记录规则

### 7.2 `version_plan.md`

建议包含：

- 当前所处版本
- `V1` 总目标
- `V1.xx` 路线图
- `V2` 展望
- 当前明确非目标

### 7.3 `changelog.md`

建议按时间倒序记录，每条包含：

- 日期
- 版本号
- 更新标题
- 产品变化
- 工程摘要
- 影响模块
- 是否需要回归测试

---

## 8. 写法原则

版本文档采用“产品主视角 + 工程摘要”写法：

- 主文案优先写学生和老师会感受到什么变化
- 工程部分只写必要摘要，不写成技术流水账
- `version_plan.md` 不替代 task plan
- `changelog.md` 不替代 commit history
- `version_policy.md` 不替代 harness

---

## 9. 非目标

本设计不包含：

- 自动版本号生成规则
- Git tag 规范
- 发布脚本
- CI/CD 发布流
- 历史旧文档的大规模重命名

---

## 10. 推荐落地顺序

1. 先建立 `docs/common/version_policy.md`
2. 再建立 `docs/common/version_plan.md`
3. 再建立 `docs/common/changelog.md`
4. 第一条 changelog 从 `V1.01` 开始写
5. 后续只有成体系的一轮更新，才新增一个 `V1.xx`

---

## 11. 验收标准

版本治理落地后，应满足：

1. 团队能明确区分大版本和小版本的含义
2. 新更新不再随意使用零散版本命名
3. 任何人都能快速看出当前项目处于哪个阶段
4. 任何人都能从 changelog 看出某个版本对学生端和系统端分别带来了什么变化
5. `version_plan.md` 能作为项目级路线图，而不与 harness 和 task plan 串味
