# 打卡复盘流式状态输出设计

## 目标

在不改动当前 review 输出 schema、不提前做多段生成的前提下，把学生端“提交打卡后长时间黑盒等待”的体验改成：

1. 提交成功后立即进入 `pending`
2. 前端能持续看到后端当前进行到哪一步
3. review 一旦完成，仍复用现有完整详情接口渲染正式复盘
4. 任意流式能力失效时，自动退回当前轮询方案

本轮只做**流式状态**，不做**流式正文**。

---

## 一、范围边界

### 本轮做

- 后端新增单条 checkin 的 SSE 状态接口
- review 生成链路加入固定阶段埋点
- 学生端在 `pending` 时优先订阅流式状态
- 流不可用时自动退回现有轮询
- 右侧复盘工作台改成“阶段状态卡 + 完成后正式复盘”

### 本轮不做

- review 正文 token 级流式输出
- 多段生成 / 分字段生成 / Partial Mode
- 改动 review 的 JSON schema
- 改动现有 parse / guard / normalize 主链
- 新建页面或模式切换
- WebSocket

---

## 二、问题判断

当前 review 在默认 `32768` 上限下已经能恢复正文，但单题常见耗时仍在 `50~80s`。  
对学生来说，当前最差的不是“最终拿不到复盘”，而是：

- 提交后只能看到静态 `pending`
- 不知道系统是否还活着
- 不知道当前卡在“模型调用”还是“后处理”

因此，本轮最合适的目标不是继续改正文生成方式，而是先把**等待黑盒变成阶段可见**。

---

## 三、设计原则

### 1. 阶段来源必须是手动埋点

当前 review 仍是整段调用，不存在天然的 token 级阶段切点。  
为了守住“本轮不做多段生成”的边界，本轮固定采用：

- 在现有 review 主链前后插入固定节点
- 由这些节点推送阶段事件

不做：

- 按内容段落切割生成
- 按字段逐段生成
- 依据 token 实时内容推断阶段

### 2. 流只负责状态，不负责正文

流式接口只传：

- 当前状态
- 当前阶段
- 阶段文案
- 事件时间

不传：

- 半截 JSON
- 未过 guard 的原始复盘正文
- 中途草稿

### 3. 完整复盘仍从现有详情接口读取

流式事件只负责告诉前端：

- “复盘已经就绪，可以刷新完整内容”

一旦收到 `review_ready` 或 `completed`，前端继续调用现有：

- `GET /api/checkins/{checkin_id}`

来拿正式结构化复盘。

### 4. 必须兼容当前轮询链

SSE 只作为当前 `pending` 体验的增强层。  
如果订阅失败、浏览器断流、后端未返回事件，前端必须自动退回现有轮询：

- 不影响 `pending / failed / completed`
- 不影响重试按钮
- 不影响 A/B/C 学习闭环后续动作

---

## 四、后端接口设计

### 新增接口

- `GET /api/checkins/{checkin_id}/stream`

返回：

- `Content-Type: text/event-stream`

鉴权：

- 通过 `require_student`
- 只允许当前学生订阅自己的 checkin
- 不属于当前学生时返回 `404`

### 事件格式

统一使用 SSE 标准事件：

```text
event: status
data: {"checkin_id":123,"review_status":"pending","phase":"llm_start","message":"正在调用模型","elapsed_seconds":12}
```

### 事件类型

- `status`
- `review_ready`
- `error`
- `keepalive`

说明：

- `status`：阶段变化或等待时长更新
- `review_ready`：review 已可从详情接口读取
- `error`：本轮生成失败
- `keepalive`：长连接保活，前端不渲染

---

## 五、阶段定义

本轮阶段固定为手动埋点，不依赖模型内部事件。

### 1. `received`

触发时机：

- `POST /api/checkins` 成功入库后

学生文案：

- `已收到打卡`

### 2. `queued`

触发时机：

- review 后台任务已创建，等待执行

学生文案：

- `已进入生成队列`

### 3. `llm_start`

触发时机：

- 后台线程刚开始调用 `generate_review(...)`

学生文案：

- `正在调用模型`

附加信息：

- 前端可显示“已等待 X 秒”

### 4. `llm_done`

触发时机：

- LLM 已返回可用正文

学生文案：

- `模型已返回，正在整理内容`

### 5. `review_parse`

触发时机：

- 开始 parse / guard / normalize

学生文案：

- `正在整理复盘内容`

### 6. `review_saved`

触发时机：

- review 已写库完成

学生文案：

- `复盘已生成，正在准备理解检查`

### 7. `quiz_generating`

触发时机：

- 开始生成 quiz / self-check / confirm 前置内容

学生文案：

- `正在准备理解检查`

### 8. `completed`

触发时机：

- 单条 checkin 工作台所有当前应展示内容已就绪

学生文案：

- `复盘已就绪`

### 9. `failed`

触发时机：

- 任一步异常、超时、或 review 最终失败

学生文案：

- `复盘生成失败，可稍后重试`

---

## 六、后端状态源

为了让 SSE 能持续推送，本轮需要在服务端保留一份**短生命周期的单条 checkin 运行时状态**。

建议使用进程内状态表：

- key：`checkin_id`
- value：
  - `phase`
  - `review_status`
  - `message`
  - `updated_at`
  - `started_at`

要求：

- 只作为运行时状态使用
- 不单独落数据库
- `completed / failed` 后保留短时间即可清理

原因：

- 本轮只是状态增强，不需要引入新的持久化表
- 当前只有本地单实例联调目标，先不引入 Redis 或消息队列

---

## 七、前端行为

### 1. 提交后

学生提交打卡成功后：

- 如果 `review_status = pending`
- 先立即渲染 `pending` 状态卡
- 再尝试订阅 `GET /api/checkins/{checkin_id}/stream`

### 2. 订阅成功时

右侧工作台改为展示：

- 当前阶段标题
- 当前阶段文案
- 等待秒数
- 当前题目标题

示例：

- 已收到打卡
- 正在调用模型（已等待 18 秒）
- 正在整理复盘内容

### 3. 收到 `review_ready` 或 `completed` 时

前端立即：

1. 关闭流式订阅
2. 请求 `GET /api/checkins/{checkin_id}`
3. 用现有 `renderReviewHtml(...)` 渲染完整复盘

### 4. 收到 `error` 时

前端立即：

1. 关闭流式订阅
2. 切换到现有失败卡
3. 保留“重新生成”按钮

### 5. 流式失败时

如果：

- SSE 连接失败
- 浏览器不支持
- 长时间没有状态更新

则自动退回：

- 现有 `pollCheckinReviewStatus(...)`

即：

- 先流式
- 失败再轮询

不是：

- 流式和轮询同时并行

---

## 八、前端文案边界

本轮前端只展示系统阶段，不展示原始模型内容。

允许展示：

- 已收到打卡
- 已进入生成队列
- 正在调用模型
- 正在整理复盘内容
- 正在准备理解检查
- 复盘已就绪
- 复盘生成失败，可稍后重试

不展示：

- 原始 JSON 字段名
- 原始错误堆栈
- 模型原始回复片段
- 队列序号

---

## 九、失败与异常处理

### 1. review 失败

当 review 最终失败：

- SSE 推送 `error`
- `review_status = failed`
- 学生端展示现有失败卡

### 2. 流连接中断

如果连接中断但 checkin 仍是 `pending`：

- 前端自动退回轮询

### 3. 后端状态源缺失

如果流式接口发现：

- 当前 `checkin_id` 没有运行时阶段信息
- 但数据库状态是 `pending`

则返回一个保守阶段：

- `phase = queued`
- `message = 已进入生成队列`

保证学生端不会看到空白状态

---

## 十、验收标准

### 接口验收

1. `GET /api/checkins/{checkin_id}/stream` 能返回标准 SSE
2. 学生只能订阅自己的 checkin
3. review 完成时，流会发出 `review_ready` 或 `completed`
4. review 失败时，流会发出 `error`

### 前端验收

1. 提交后不再只是静态 `pending`
2. 学生能看到阶段变化
3. 流失败时会自动退回现有轮询
4. `completed` 后仍使用现有完整详情接口渲染正式复盘
5. 不破坏当前 `failed / retry / A/B/C` 链路

### 产品验收

1. 用户等待时不再是黑盒
2. 本轮无需真正流正文，也能明显改善等待体验
3. 现有结构化 review 主链不需要重写

---

## 十一、后续但不在本轮

如果本轮验证“阶段流式状态”明显改善体验，后续才考虑：

1. review 按字段分阶段生成
2. Partial Mode / 续写补全
3. 真正的正文流式拼接
4. 更细粒度的队列/时长统计

本轮 spec 不包含以上实现。
