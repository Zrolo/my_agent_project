# NOI Review + Quiz 质量闭环设计

## 目标

为当前 NOI 教练系统补第一版 `AI 复盘 + quiz` 质量闭环。

这轮先不直接修改 prompt、guard 或前后端实现，而是先定义：

1. 什么样的 `review` 可以放行
2. 什么样的 `quiz` 可以放行
3. 什么情况必须退回 `fallback_explain`
4. 后续改动后，应该如何复测

这份设计只覆盖当前已知最不稳定的 4 个 focus：

- `general_modeling`
- `constraint_modeling`
- `greedy_basis`
- `method_selection`

---

## 本轮非目标

这轮不做：

- 扩展到全部 focus
- 直接提高 quiz 覆盖率
- 学生端视觉改版
- 老师端新页面
- 自动化评测平台
- 新一轮 prompt 调参

---

## 设计原则

1. 先立质量门，再做实现优化。
2. 宁可 `fallback`，也不放坏题。
3. `review` 是上游，`quiz` 必须建立在正确桥梁判断之上。
4. harness 只写硬边界，NOI 专项文档只写教学样例和评分细则。
5. 第一版只求小而硬，不求全。

---

## 文档分层

### 1. Harness 层

新增文件：

- `docs/harness/review_quiz_quality_gate.md`

职责：

- 定义 `review` 放行条件
- 定义 `quiz` 放行条件
- 定义 `fallback_explain` 必触条件
- 定义复测门触发条件

这份文件属于运行契约。
它应该是跨 focus 通用的最小质量规则，不放具体题目样例，不放某次调参经验。

### 2. NOI 专项层

新增文件：

- `docs/subjects/noi/focus_quality_eval_v1.md`

职责：

- 记录 4 个高风险 focus 的评测样例
- 记录每组样例的预期行为
- 记录统一评分 rubric
- 记录典型滑坡坏例

这份文件属于教学质量专项文档。
它可以随着 focus 迭代继续增补，但不应该上升为全局系统契约。

## 质量门

### 一、Review 放行条件

一个 `review` 只有同时满足下面条件，才算可继续进入 quiz 阶段：

1. `key_bridge` 必须对应学生这次真实卡住的那一步。
2. `next_step` 必须是当前桥梁下的一个可执行小步，不是泛泛建议。
3. 输出不能滑成泛化学习建议、方法口号或“以后遇到这类题就...”。
4. 不能用同类题套路替代本题结构判断。
5. 学生向字段 `main_block / key_bridge / next_step / transfer_signal` 必须对得上同一个结构问题，不能各说各话。

### 二、Quiz 放行条件

一个 `quiz` 只有同时满足下面条件，才算可放给学生：

1. 正确答案必须是结构事实，不是学习建议。
2. 题目必须贴原题语境，测的是当前桥梁，而不是泛算法常识。
3. `main / followup / confirm` 都必须围绕同一桥梁展开。
4. 每个错误选项都必须对应一个具体结构误区。
5. `bridge_feedback` 必须说明学生答对的是哪一步结构事实，以及它和原题卡点的关系。
6. `distractor_feedback` 必须指出该错误选项具体错在哪个结构，而不是笼统地说“这个不对”。

### 三、Fallback 必触条件

出现下面任一情况，必须退回 `fallback_explain`，不允许硬出题：

1. 当前桥梁无法稳定落成结构事实题。
2. 模型产出的正确答案本质上属于 `learning_advice`。
3. 题目已经滑成口号题、策略题、泛方法题。
4. `confirm` 的新情境里，核心结构事实已经变化，而不只是表面场景变化。

这里的“核心结构事实变化”重点看这些对象是否变了：

- 状态含义
- 转移条件
- 建模对象

如果这些核心结构已经变了，就不是在验证同一桥梁，而是在换题。

### 四、Fallback 克制规则

`fallback_explain` 的职责只限于：

- 明确说明当前桥梁不适合出结构事实题

它不应做这些事：

- 展开完整讲解
- 替代 `remedy`
- 偷偷变成一段新的教学正文

换句话说，`fallback_explain` 是停止坏题外放的守门动作，不是另一个补救模块。

## 评测集设计

专项评测文档只覆盖这 4 个 focus：

- `general_modeling`
- `constraint_modeling`
- `greedy_basis`
- `method_selection`

### 每个 focus 的固定样例结构

每个 focus 第一版先放 3 组样例：

1. `应放行`
2. `应 fallback`
3. `易滑坡坏例`

合计 12 组。

### 三类样例的职责

#### `应放行`

用于验证：

- 当前 focus 在理想输入下，是否能稳定产出合格 review 和 quiz

#### `应 fallback`

用于验证：

- 系统在不适合出题时，是否会主动停手，而不是强出坏题

#### `易滑坡坏例`

用于验证：

- 现有 prompt 和 guard 最容易漏掉的坏输出，是否已经被拦住

### 样例优先级

3 组样例里，`易滑坡坏例` 优先级最高。

原因：

- 它最容易在当前系统里被误放行
- 它最能暴露 prompt 和 guard 的薄弱点
- 第一版先把最危险的坏输出拦住，收益最高

建议的落地顺序：

1. 先写 `易滑坡坏例`
2. 再写 `应 fallback`
3. 最后写 `应放行`

### 每组样例的最少字段

每组样例至少包含：

- 原题简述
- 学生卡点
- 期望 `review` 方向
- 期望 `quiz` 行为
- 是否应 fallback
- 判坏理由

---

## 统一评分 Rubric

所有样例统一按下面 5 项判断：

1. 桥梁是否对
2. 是否是结构事实
3. 是否贴原题语境
4. 反馈是否具体指出结构差错
5. fallback 是否克制

### 1. 桥梁是否对

判断 `review` 抓到的 `key_bridge` 是否真是学生当前缺的那一步。

如果桥梁抓错，后面 quiz 再完整，也视为失败。

### 2. 是否是结构事实

判断 `quiz` 的正确答案是不是：

- 定义
- 关系
- 条件
- 顺序
- 维护量
- 代价或状态含义

如果本质上只是学习建议或方法口号，则视为失败。

### 3. 是否贴原题语境

判断输出有没有脱离原题，变成泛算法教学。

只要脱离原题语境，就算它内容看起来“有道理”，也不通过。

### 4. 反馈是否具体指出结构差错

判断：

- `bridge_feedback`
- `distractor_feedback`

是否明确指出了学生答对或答错的具体结构点。

如果只是“这个不对”“要注意这里”这类空话，则视为失败。

### 5. Fallback 是否克制

判断 `fallback_explain` 是否只承担守门职责。

合格标准：

- 只说明当前桥梁不适合出结构事实题
- 不展开长讲解
- 不替代 `remedy`

---

## 放行与复测规则

### 一、单条样例通过标准

出现下面任一情况，单条样例直接判不通过：

- 桥梁判断错
- 正确答案不是结构事实
- 输出脱离原题语境
- `confirm` 已经换了核心结构事实
- 反馈没有指出具体结构问题

### 二、单个 Focus 通过标准

一个 focus 要通过，至少要满足：

1. `应放行` 样例不能产出明显坏题
2. `应 fallback` 样例不能被错误放行为 quiz
3. `易滑坡坏例` 不能继续被系统误判为合格输出

### 三、整体放行标准

这 4 个 focus 都没有明显退化，才允许继续推进实现层改动。

---

## 复测门触发条件

### 必须全量复测的变更

以下任一改动，必须复测全部 12 组样例：

- `review prompt` 改动
- `quiz prompt` 改动
- 全局 `system.md` 级规则改动
- 后端通用 guard 函数改动

### 只需局部复测的变更

以下改动，只需复测受影响 focus 的 3 组样例：

- 单个 focus snippet 改动

如果一次提交同时碰了多个 focus snippet，就复测对应多个 focus。

---

## 推荐实施顺序

1. 先写 `docs/harness/review_quiz_quality_gate.md`
2. 再写 `docs/subjects/noi/focus_quality_eval_v1.md`
3. 再进入实现计划阶段

这样排的原因是：

- 先写质量门，能防止评测样例失去统一标准
- 再写样例，能把“什么叫好和坏”落成可复用材料
- 最后才写实现计划，能避免边设计边改代码

---

## 后续实现约束

这份 spec 通过后，下一步实现应遵守下面边界：

1. 优先处理 `review -> key_bridge / next_step` 的稳定性。
2. 不要为了提高 coverage 去放松 fallback 门槛。
3. 每次只改一类规则，再回跑评测样例。
4. 不做“大杂烩式联改”，避免回归来源不可追踪。

---

## 验收标准

这份设计进入实施前，应达到：

1. 两份新文档的位置和职责已经明确
2. `review / quiz / fallback / confirm` 的边界已经写清
3. 4 个高风险 focus 的评测范围已经收敛
4. 样例结构、rubric、复测门都能直接指导后续实现
5. 没有把 prompt 调参细节混进 harness 契约
