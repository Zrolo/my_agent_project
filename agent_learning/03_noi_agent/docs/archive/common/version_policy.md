# 版本治理规则

## 1. 版本治理目的

- 统一项目版本命名
- 让版本号优先表达产品阶段，而不是零散代码批次
- 让后续更新有固定记录方式

## 2. 编号规则

- 大版本：`V1`、`V2`、`V3`
- 小版本：`V1.01`、`V1.02`、`V1.03`

## 3. 大版本升级条件

只有当学生使用体验或教学闭环进入新阶段时，才升大版本。

例如：

- 从“能提供 AI 复盘”进入“能稳定完成复盘 + quiz + remedy 闭环”
- 从“规则型推荐”进入“稳定个性化训练路径”
- 从“以人工调参为主”进入“以稳定评测与版本治理为主”

## 4. 小版本升级条件

同一阶段内的成体系增强、质量收紧、体验改良、工程维护，升小版本。

例如：

- AI 复盘质量收紧
- quiz / fallback / confirm 规则收紧
- 学生端工作台体验增强
- 教师端运营能力增强
- 题库与 problem analysis 质量增强
- 一轮明确边界的工程整理

不要求每个 commit 都对应一个小版本。

## 5. 版本状态

- `planned`
- `in_progress`
- `released`
- `archived`

含义：

- `planned`：已进入版本路线图，但尚未开始
- `in_progress`：已经围绕该版本主题推进
- `released`：该版本目标已达到当前定义的完成线
- `archived`：保留历史记录，不再继续扩写

## 6. 记录规则

- `version_policy.md` 只写规则
- `version_plan.md` 只写规划
- `changelog.md` 只写已发生变化
- 每次成体系版本更新后，必须同步检查并更新这三份文档：
  - `version_policy.md`
  - `version_plan.md`
  - `changelog.md`
- 如果其中某一份本轮无需改动，也应在本轮确认其内容仍然有效
- 不单独建立 `update.md`
- 新版本治理从 `V1.01` 开始生效
- 旧文档中的历史版本命名保留原样，不作为新的统一治理基线
