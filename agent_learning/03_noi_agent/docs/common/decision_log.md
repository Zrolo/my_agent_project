## 结构型 Quiz 替代抽象元认知 Quiz
- 日期：2026-04-01
- 适用范围：通用方法，NOI 先落地
- 关联版本：v1.2

#### 问题
- 旧版 quiz 太像“元认知判断题”，常见题干是：
  - `这一步更该先做什么？`
  - `这一步更该先看清哪件事？`
- 这类题对初中生过于抽象，学生容易在猜“老师想听哪句正确口号”，而不是在真正判断当前结构。
- 从老师视角看，这类题测出的更多是“学生知不知道方法口号”，不是“学生会不会做这一步”。

#### 原方案的问题
- 题目太抽象，学生经常不知道“这一步”具体指什么。
- 答对后也难以证明学生真的懂了，很容易出现“假懂”。
- main / followup / confirm 三层虽然流程上存在，但内容上区分不够明显，confirm 容易退化成“再来一题更简单的”。
- 答错时通常只会得到泛化反馈，无法指出“选中的这个错误选项到底错在哪个结构”。

#### 最终决策
- 将 quiz 从抽象元认知题升级成“结构型小题”。
- 结构型小题只测当前桥梁对应的一小层结构，例如：
  - 状态定义
  - 转移关系
  - check 条件
  - 枚举顺序
- 三层职责明确区分：
  - `main quiz`：优先用原题对象和原题语境出题
  - `followup quiz`：仍用原题语境，但更小、更单步
  - `confirm quiz`：优先换一个更小的新情境，验证同一桥梁是否能迁移
- 题目只能是结构判断题，不能是计算题。
- 一次 LLM 调用同时输出：
  - 题目
  - 正确解释
  - `bridge_feedback`
  - `distractor_feedback`
- 学生答对时优先展示 `bridge_feedback`，答错时优先展示所选项对应的 `distractor_feedback`。

#### 不采用的备选方案
- 继续使用抽象桥梁题：
  - 没选，因为它测的是“会不会说口号”，不是“会不会做这一步”。
- 按“同算法”直接再出一道类似题：
  - 没选，因为同一个算法里可能卡的是完全不同的桥，粒度太粗。
- 把 confirm 做成“更简单”的同类题：
  - 没选，因为这只会增加熟悉感，不足以证明迁移理解。
- 答错后直接展示完整正确解释：
  - 没选，因为这会重新滑回“系统替学生走路”，不能指出学生选中的错误结构。
- 用开放聊天补救：
  - 没选，因为边界失控，且会削弱系统主流程和证据链。

#### 教学理由
- 从老师视角看：
  - 结构型小题比抽象判断题更有证据价值，能看出学生到底会不会识别正确结构。
  - `main / followup / confirm` 分层后，可以更清楚地区分：
    - 原题语境下能不能做
    - 有脚手架后能不能做
    - 换情境后能不能迁移
  - `distractor_feedback` 让老师看到学生具体偏在哪种错误理解上，而不是只知道“答错了”。
- 从学生视角看：
  - 结构型小题更像一小步真实训练，而不是在猜老师想听什么。
  - `bridge_feedback` 能告诉学生“我刚才到底答对了哪一步”。
  - `distractor_feedback` 能告诉学生“我选的这个为什么错”，比直接看标准答案更能帮助修正。

#### 实现影响
- Prompt 层：
  - 重构为 `system/user + snippets`
  - 增加结构型 quiz 规则、错误选项反馈规则、桥梁反馈规则
- 生成层：
  - `review_engine.py`
  - main / followup / confirm 全部开始支持结构型小题
- 数据层：
  - `database.py`
  - quiz 记录支持 `bridge_feedback`、`distractor_feedback`
- 接口层：
  - `api_server.py`
  - 答对 / 答错分流返回不同反馈
- 前端层：
  - `static/app.js`
  - 支持对象数组选项渲染，支持按所选项展示错因反馈

#### 是否可跨学科复用
- 可以（方法层面）
- 原因：
  - “抽象口号题 -> 结构型小题”的转向，本质上是通用教学原则，不只适用于 NOI。
  - `main / followup / confirm` 的职责划分，属于跨学科可复用的学习流程设计。
  - `bridge_feedback / distractor_feedback` 的答对/答错分流，也适用于其他学科。
  - 需要按学科单独替换的是：
    - focus 地图
    - 典型误区
    - 结构型题目的具体对象与术语
