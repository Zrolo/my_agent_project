# OI Wiki Pedagogical Rewrite Rules v1

## 目标

这份文档定义：

- `OI Wiki` 原文怎么转成学生端能听懂的 bridge 知识卡
- 哪些内容可以保留
- 哪些内容必须改写

## 基本原则

`OI Wiki` 在我们系统里负责：

- 提供正确知识
- 提供术语边界
- 提供章节定位

它不直接负责：

- 学生端讲解
- 小测文案
- 补课语气

## 改写规则

### 1. 先讲对象，再讲关系

不要直接写：

- `Trie 是一个维护字符串集合的数据结构`

优先改成：

- `很多字符串前面一段一样，而且还要反复按前缀查`
- `这时候可以先把相同开头合在一起看`

### 2. 一次只保留一座桥

不要把：

- 定义
- 实现
- 复杂度
- 多个用途

一次全讲给学生。

每次只保留：

- 当前这一步最容易误会什么
- 当前这一步真正要站稳什么

### 3. 术语保留，但必须翻译

可以保留术语：

- `trie`
- `状态`
- `状态转移`
- `lazy`
- `判定函数`

但必须紧跟学生话解释。

例如：

- `lazy 标记`
  - 不是“代码还没跑”
  - 而是“这段区间已经欠了一个更新，还没往下告诉孩子”

### 4. 优先给最小例子

如果 `OI Wiki` 原文只有定义，没有例子：

- 不直接照抄
- 要补一个最小例子

### 5. 不直接展示原代码模板

第一版 bridge 知识卡里：

- 不直接把 `OI Wiki` 的代码贴给学生
- 代码模板只作为老师参考或后续实现参考

## 推荐映射

### `method_selection`

- 适合从 OI Wiki 里抽：
  - 什么时候用这个结构/算法
- 学生端改写成：
  - `题面里什么信号支持这个方法`

### `shared_prefix_merging`

- 适合从 OI Wiki 里抽：
  - 共用前缀路径
  - 查询沿路径走
- 学生端改写成：
  - `为什么很多相同开头值得先合起来看`

### `lazy_semantics`

- 适合从 OI Wiki 里抽：
  - 节点维护区间信息
  - 修改与查询如何拆开
- 学生端改写成：
  - `lazy 到底在节点上表示什么`

## 一句话

`OI Wiki` 原文进入我们系统后，必须先经过：

- **桥级切片**
- **学生化改写**
