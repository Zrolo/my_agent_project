# NOI 专项评测样例文档 v1

## 本文件的写入标准

这份文档只写 NOI 专项评测层该有的内容：

- 4 个高风险 focus 的评测模板
- 样例优先级
- 统一 rubric
- 典型坏例约束

不要写：

- harness 级跨 focus 质量门全文
- prompt 调参过程
- 通用守门逻辑的重复定义
- 与这 4 个 focus 无关的教学扩展

---

## 一、覆盖范围与优先级

本版只覆盖下面 4 个 focus：

1. `general_modeling` - 最高优先
2. `constraint_modeling` - 最高优先
3. `greedy_basis` - 次高优先
4. `method_selection` - 次高优先

### 样例组执行优先级

每个 focus 内部固定按下面顺序评测：

1. `易滑坡坏例`
2. `应 fallback`
3. `应放行`

说明：

- `易滑坡坏例` 优先级最高，因为它最容易漏放到学生端
- `应 fallback` 用来确认系统会主动停手，不会硬出坏题
- `应放行` 用来确认在理想输入下能稳定产出合格 review 和 quiz

---

## 二、统一样例模板

每组样例都必须记录下面字段：

- 原题简述
- 最小复测输入
- 学生卡点
- 期望 `review` 方向
- 期望 `quiz` 行为
- 期望 `quiz` 角色
- 是否应 fallback
- 判坏理由
- 实际 `review` 输出（跑完后填）
- 实际 `quiz` 输出（跑完后填）

### 最小复测输入写法

为了保证不同 reviewer 能复跑同一条样例，`最小复测输入` 至少要写成下面这种标准化表达：

- `problem_context = ...`
- `bottleneck_text = ...`
- 必要时补一条 `submission_result = ...` 或 `student_code = ...`

不要只写摘要，不写可喂给系统的最小输入。

### 通过标准写法

不要写“明显坏题”这类模糊判断。  
通过与否必须直接对照 harness 质量门条件来写：

- `review` 是否满足放行条件
- `quiz` 是否满足放行条件
- 是否命中 `fallback_explain` 必触条件
- `fallback_explain` 是否保持克制

## 三、统一 Rubric

所有 focus 都按同一组 rubric 判断：

1. 桥梁是否对
2. 是否是结构事实
3. 是否贴原题语境
4. 反馈是否具体指出结构差错
5. fallback 是否克制

### 1. 桥梁是否对

看 `review` 抓到的 `key_bridge` 是否真是学生这次卡住的那一步。

### 2. 是否是结构事实

看 `quiz` 正确答案是不是结构事实，而不是学习建议、方法口号或泛化表达。

### 3. 是否贴原题语境

看题目和选项是否仍然在验证原题里的那座桥，而不是换成同类题常识。

### 4. 反馈是否具体指出结构差错

看 `bridge_feedback` 和 `distractor_feedback` 是否明确说出错在什么结构上。

### 5. fallback 是否克制

看 `fallback_explain` 是否只负责说明当前桥梁不适合出结构事实题，不展开补讲。

---

## 四、通过标准

### `应放行`

- `review` 必须同时满足 harness 质量门中的 5 条放行条件
- `quiz` 必须同时满足 harness 质量门中的 6 条放行条件

### `应 fallback`

- 必须命中至少 1 条 `fallback_explain` 必触条件
- 不得被错误放行为结构 quiz

### `易滑坡坏例`

- 只要出现口号题、泛方法题、桥梁错位，直接判坏
- 只要 `confirm` 换了核心结构事实，直接判坏

### 4.1 `general_modeling`

#### 样例组 A：`易滑坡坏例`

- 原题简述：题目给出“课程先修关系”，问应怎样建模成图。
- 最小复测输入：`problem_context = 课程之间有先修关系，问怎样表示课程依赖； bottleneck_text = 我知道像图，但分不清课程和依赖关系分别放在哪里。`
- 学生卡点：只会说“把关系画成图”，但分不清点是课程、边是先修关系。
- 期望 `review` 方向：抓住“点/边各代表什么”这个桥梁，不要上升成“建图思路”口号。
- 期望 `quiz` 行为：问点和边分别对应什么，题目语境要贴着课程先修关系。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：如果 review 没有落到“点/边对应什么”，就不满足 `key_bridge` 对应具体结构的放行条件；如果 quiz 只问“是不是建图”，就不是结构事实题。

#### 样例组 B：`应 fallback`

- 原题简述：题目只说“比较哪个方案更合理”，没有稳定的对象集合，也没有明确关系类型。
- 最小复测输入：`problem_context = 题目只要求比较两个方案哪个更合理，没有给稳定对象和关系类型； bottleneck_text = 我想把它翻成图，但不知道点和边到底是什么。`
- 学生卡点：想强行把它翻成图，但题面没有足够信息落到点和边。
- 期望 `review` 方向：说明当前桥梁无法稳定落成结构事实题，先停手。
- 期望 `quiz` 行为：退回 `fallback_explain`，不要硬出图建模题。

- 判坏理由：这里如果继续出题，只会把“合理”改写成空泛建模口号，既不贴原题，也不是真结构题。

#### 样例组 C：`应放行`

- 原题简述：题目给出“房间之间能直接连通”，问图里点和边怎么表示。
- 最小复测输入：`problem_context = 房间之间有若干直接连通关系，问如何建图表示； bottleneck_text = 我知道要建图，但总把房间和连通关系混着写。`
- 学生卡点：能想到图，但容易把“房间”与“连通关系”混成一个概念。
- 期望 `review` 方向：确认学生卡在“对象怎么抽象成点、关系怎么抽象成边”。
- 期望 `quiz` 行为：正确结构事实必须是“点表示房间，边表示房间之间可直接连通”；错误选项至少包含“点表示连通关系、边表示房间”和“点表示一次移动、边表示房间编号”。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：题面已具备对象与关系两类稳定元素，可直接检验结构事实，不命中 `fallback_explain` 必触条件。

#### 典型坏例约束

- 不允许把“对象与关系”写成空泛口号，必须落到具体点、边、可达关系或等价映射
- 不允许题干只问“先看什么”，必须能检查学生是否真的会把题面对象抽成结构
- 不允许选项只是在背方法名，必须能对应到具体建模误区
- 不允许 `quiz` 的正确答案变成“多观察、多思考”这类学习建议

### 4.2 `constraint_modeling`

#### 样例组 A：`易滑坡坏例`

- 原题简述：题目给出“每个活动都有时间和地点限制”，问如何整理这些限制。
- 最小复测输入：`problem_context = 每个活动都必须同时满足时间窗口和指定地点这两个条件，才算合法安排； bottleneck_text = 我知道题里有两个限制，但总把它们看成一个主条件加一个顺手检查。`
- 学生卡点：分不清这两个限制是并列同时满足，还是“主条件 + 附带提醒”。
- 期望 `review` 方向：明确指出当前桥梁是“两个限制如何组成同一个合法性条件”，不要转成泛泛的读题提醒。
- 期望 `quiz` 行为：直接问“合法安排”的判定结构是哪一种；正确结构事实必须是“时间和地点同时满足”，错误选项至少包含“只看时间、地点顺手检查”和“二选一满足即可”。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：如果 review 没落到“并列同时满足”这个桥梁，或 quiz 没能区分“同时满足”与“主条件+附带提醒/二选一”，就不满足同桥与结构事实要求。

- 实际 `quiz` 输出（跑完后填）：

#### 样例组 B：`应 fallback`

- 原题简述：题目只有“人数不能超过 k”这一条上限，没有第二条限制，也没有限制之间的关系可整理。
- 最小复测输入：`problem_context = 题目只要求人数不能超过 k，除此之外没有别的限制关系； bottleneck_text = 我想知道这些限制怎么一起建模，但题面其实只有一个上限。`
- 学生卡点：把“单条上限”误当成“多个限制之间的关系建模”来问。
- 期望 `review` 方向：指出当前输入里没有“限制之间的关系”可测，当前桥梁不成立，应停在 fallback。
- 期望 `quiz` 行为：直接退回，不把“单条上限”伪装成约束关系题。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：是。
- 判坏理由：这里只有单条限制，没有“并列/择一/前后依赖”这类关系结构；若继续出题，就无法稳定落成约束关系的结构事实题，命中 `fallback_explain` 必触条件。

#### 样例组 C：`应放行`

- 原题简述：题目给出“每件物品必须同时满足重量和体积上限”。
- 最小复测输入：`problem_context = 每件物品都必须同时满足重量上限和体积上限； bottleneck_text = 我看到了两个限制，但总把它们当成二选一。`
- 学生卡点：能看到两个限制，但总把“同时满足”误读成“满足一个主要限制就行，另一个只是补充”或“二选一”。
- 期望 `review` 方向：抓住“重量和体积是并列同时生效的合法性条件”。
- 期望 `quiz` 行为：正确结构事实必须是“重量和体积同时满足才合法”；错误选项至少包含“只要重量满足即可”“两者满足其一即可”这两类误区。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：题面已明确给出两个并列限制，可直接检验“同时满足”的结构事实，不命中 `fallback_explain` 必触条件。
- 实际 `review` 输出（跑完后填）：
- 实际 `quiz` 输出（跑完后填）：

#### 典型坏例约束

- 不允许把约束转换成“注意边界”“小心分类”这种泛提醒
- 不允许只测一个显式条件，必须能看出学生有没有抓到约束之间的关系
- 不允许把约束结构写成算法套路题，题干要能对应到具体限制关系
- 不允许 `distractor_feedback` 只说“这项不对”，必须指出是哪条约束关系错了

### 4.3 `greedy_basis`

#### 样例组 A：`易滑坡坏例`

- 原题简述：题目要求从若干互不相同的区间任务里选出最多个互不重叠的任务。
- 最小复测输入：`problem_context = 有 n 个区间任务，每个任务有开始和结束时间，目标是最大化可选任务数，且选中的任务之间不能重叠； bottleneck_text = 我知道常见做法是先选结束时间早的，但说不清这个选择为什么不会吃亏。`
- 学生卡点：只会背“贪心要先选最优”，说不出为什么这个选择是安全的。
- 期望 `review` 方向：抓住“为什么这个局部选择不会破坏后续解”。
- 期望 `quiz` 行为：问“先选结束时间最早的区间”为什么能保留更多后续可兼容区间，而不是问“这是不是贪心”。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：如果把题面改成“贪心有什么优点”，就会滑成泛方法题。

#### 样例组 B：`应 fallback`

- 原题简述：题面只说“通常先选代价最小的方案更好”，但没有目标函数、可兼容条件或交换依据。
- 最小复测输入：`problem_context = 题目只给出一句经验结论：通常先选代价最小的方案更好；没有说明目标是最大化什么，也没有说明方案之间如何冲突； bottleneck_text = 我想套贪心，但看不出这个局部选择和最终目标有什么关系。`
- 学生卡点：想硬套贪心模板，但没有可判断的安全性依据。
- 期望 `review` 方向：说明当前桥梁不适合稳定出结构事实题。
- 期望 `quiz` 行为：退回 fallback，不编一个“看起来像贪心”的口号题。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：是。
- 判坏理由：没有可检验的安全性条件，硬出题只会测套路记忆。

#### 样例组 C：`应放行`

- 原题简述：题目要求选出最多个互不重叠区间，问为何优先选结束时间最早的区间。
- 最小复测输入：`problem_context = 有 n 个区间，目标是最大化选出的区间数量，且任意两个被选区间不能重叠； bottleneck_text = 我知道常见做法是先选结束时间最早的区间，但不知道它为什么能留下最多后续空间。`
- 学生卡点：知道要选早结束的，但不清楚它为什么保留更多后续空间。
- 期望 `review` 方向：稳定测“局部选择为什么安全”这件事。
- 期望 `quiz` 行为：正确结构事实必须是“先选结束时间最早的区间，能给后续区间留下最多可兼容空间”；错误选项至少包含“先选开始时间最早”和“先选区间长度最短”。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：题面明确给出局部选择与后续空间的关系，可直接检验贪心依据，不命中 `fallback_explain` 必触条件。

- 实际 `quiz` 输出（跑完后填）：

#### 典型坏例约束

- 不允许只问“是不是贪心”，必须问贪心选择依据是否成立
- 不允许把题目写成完整证明题，重点应落在局部选择为什么安全
- 不允许正确答案退化成“先选最优的”这类口号
- 不允许错误选项只是在换说法，必须对应具体的选择失误或安全性误判

### 4.4 `method_selection`

#### 样例组 A：`易滑坡坏例`

- 原题简述：题目给出 `n <= 20`，要求在所有子集里找最优值。
- 最小复测输入：`problem_context = n <= 20，需要枚举所有子集并从中找最优方案； bottleneck_text = 我一看到最优值就想套 DP，但没判断这个规模其实允许直接枚举。`
- 学生卡点：忽略规模上界已经足够小，误把“求最优”直接等同于“必须 DP”。
- 期望 `review` 方向：把这条桥梁固定在“规模上界是否已经允许直接枚举”，不要混入别的依据。
- 期望 `quiz` 行为：正确结构事实必须是“`n <= 20` 时可以直接枚举全部子集”；错误选项至少包含“因为求最优所以必须 DP”和“因为有很多子集所以只能贪心”。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：如果只问“这题是什么算法”，就会变成题型记忆题。

#### 样例组 B：`应 fallback`

- 原题简述：题面只说“求最优解”，没有数据范围、状态对象、约束规模或结构特征。
- 最小复测输入：`problem_context = 题目只要求求最优解，没有给 n 的范围，也没有给对象关系、状态维度或限制结构； bottleneck_text = 我完全不知道该选枚举、DP 还是别的方法。`
- 学生卡点：没法判断该用什么方法，只能猜。
- 期望 `review` 方向：说明方法边界不成立，先 fallback。
- 期望 `quiz` 行为：不硬问方法选择，直接退回。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：是。
- 判坏理由：题面特征不足，继续出题只会把方法选择变成空猜。

#### 样例组 C：`应放行`

- 原题简述：题目要求按顺序处理长度为 `n` 的序列，每个位置的最优值依赖前面多个位置的最优值。
- 最小复测输入：`problem_context = 要按顺序处理长度为 n 的序列，每个位置的答案都依赖前面多个位置已经求出的最优值； bottleneck_text = 我没抓住“当前答案依赖前面最优值”这条线，只觉得也许还能暴力枚举。`
- 学生卡点：没抓住“重复子问题 + 前缀最优值可复用”这条桥梁。
- 期望 `review` 方向：把这条桥梁固定在“当前状态依赖前面已求出的最优值”，不要再回到“规模大不大”。
- 期望 `quiz` 行为：正确结构事实必须是“当前答案依赖前面多个位置的已知最优值，适合做状态转移”；错误选项至少包含“每个位置都能独立决策，不需要复用前面结果”和“只要 n 不是特别大就直接暴力枚举”。
- 期望 `quiz` 角色：`main`
- 是否应 fallback：否。
- 判坏理由：题面同时给出规模与方法边界线索，可直接检验方法选择，不命中 `fallback_explain` 必触条件。
- 实际 `review` 输出（跑完后填）：
- 实际 `quiz` 输出（跑完后填）：

#### 典型坏例约束

- 不允许把方法选择写成题型记忆题，必须能根据题面特征判断方法边界
- 不允许只测算法名，不测题面约束、状态含义或规模特征这些结构线索
- 不允许把选项做成“哪个更高级”这种空壳比较
- 不允许 `confirm` 换掉核心结构事实，只能验证同一桥梁

---

## 六、样例判定提醒

写这些样例时，默认按下面顺序检查：

1. 先看是不是同一座桥
2. 再看能不能落成结构事实题
3. 如果不能，就应 fallback
4. 如果能，就检查题干、选项和反馈是否都围绕同一结构展开

如果某个样例会把 `review` 拉成泛化建议、把 `quiz` 拉成方法口号，或者让 `confirm` 改了核心结构事实，这个样例就应该标为坏例，不应放行。
